6. IMPLANTATION — LES TROIS MÉCANISMES DE LIEN LOCAL (pnpm 10.32.1)
================================================================================

Préalable commun aux trois méthodes : (1) committer packages/ (le stage
actuel) ; (2) les pairs sont déjà satisfaits par l'hôte (react/react-dom
19.3.0 ∈ ^18.3.1||^19 ; radix-ui 1.7.0 ∈ ^1.7.0) ; (3) pnpm.lock a
autoInstallPeers:true et excludeLinksFromLockfile:false (les liens sont
enregistrés dans le lock). Aucune commande d'installation n'a été exécutée
ici (consigne lecture seule) — les formes ci-dessous sont à valider par un
pnpm install en local.

MÉTHODE A — Workspaces pnpm (recommandée pour un vrai monorepo)
  1. Créer pnpm-workspace.yaml à la racine :
       packages:
         - 'packages/*'
  2. Dans package.json racine, dependencies :
       "@mdevs/ui": "workspace:*",
       "@mdevs/icons": "workspace:*",
  3. pnpm install
  Fichiers touchés : package.json, pnpm-lock.yaml, + pnpm-workspace.yaml
  (nouveau). Le lock passe en multi-importers (., packages/ui, packages/icons).
  Avantage : sémantique native, résolutions stables, radix-ui dédupliqué
  par le store ; inconvénient : plus gros remaniement de lockfile.
  NOTE : ne PAS lister 'apps/*' — elles gardent leurs lockfiles propres.

MÉTHODE B — Lien direct (la plus légère, zéro nouveau fichier)
  Dans package.json racine :
       "@mdevs/ui": "link:./packages/ui",
       "@mdevs/icons": "link:./packages/icons",
  puis pnpm install (équivalent : pnpm add link:./packages/ui …).
  pnpm crée des symlinks dans node_modules/@mdevs et installe les deps
  propres (radix-ui pour ui — déjà présent en 1.7.0, dédupliqué) ;
  packages/*/node_modules éventuels restent ignorés par git (règle
  « node_modules* »). Fichiers touchés : package.json + pnpm-lock.yaml
  (le lien y est enregistré, excludeLinksFromLockfile:false).

MÉTHODE C — Tarballs locaux (la plus proche des intentions des AUTEURS)
  GETTING_STARTED.md (identique dans les deux packages) prévoit
  npm install --install-links sur dossiers extraits ou npm install *.tgz.
  --install-links est propre à npm ; l'équivalent pnpm = packager puis
  installer le tarball (copie réelle, plus de dépendance au dossier source) :
       cd packages/ui    && pnpm pack --out ../../artifacts/mdevs-ui-0.2.0.tgz
       cd packages/icons && pnpm pack --out ../../artifacts/mdevs-icons-0.2.0.tgz
       pnpm add file:./artifacts/mdevs-ui-0.2.0.tgz file:./artifacts/mdevs-icons-0.2.0.tgz
  "files" de chaque package détermine le contenu du tarball (dist, src,
  catalog, licences — tout est déjà versionné). Fichiers touchés :
  package.json, pnpm-lock.yaml, + les .tgz sous artifacts/.
  Inconvénient : re-packager à chaque évolution des packages ; les tarballs
  icônes sont volumineux (2 600 × 3 formats + 2 600 svg).

CHOIX À PRÉSENTER À L'HUMAIN : A si le dépôt doit absorber durablement les
packages comme membres du monorepo ; B pour un câblage minimal et réversible ;
C pour des builds CI hermétiques au contenu de packages/. Dans les trois cas,
l'API vue par le code applicatif est IDENTIQUE (sous-chemins §2.2/§3.2).

7. LE PROBLÈME CSS CENTRAL — @mdevs/ui/styles.css EST GLOBAL
================================================================================

7.1 Constat (src/styles.css, 236 lignes + extensions.css concaténé ; mêmes
    formes dans dist/styles.css) :
      @layer mdevs {
        :root, .md-root { --md-accent:#4f46e5; --md-bg:#f4f6fb;
          --md-blur:12px; --md-radius:20px; … ; color-scheme: light; }
        .md-root[data-md-theme="dark"] { … ; color-scheme: dark; }
        .md-glass { … } /* sélecteurs .md-* nus */
      }
    - LES BONS AMORTISSEURS (absents de Vibe/Wakies) :
      (a) nomnage systématique --md-*, .md-*, [data-md-*] → zéro collision
          avec les tokens achromatiques de l'hôte ni les utilitaires Tailwind ;
      (b) @layer mdevs → priorité INFÉRIEURE aux styles non stratifiés :
          les règles hôte (globals.css hors couche) et !important gagnent
          sans lutte ; les tokens --md-* supplémentaires sur :root ne
          cassent rien tant que l'hôte ne les consomme pas.
    - LES DEUX VRAIS DÉBORDEMENTS (ceux que les scripts maison neutralisent
      depuis toujours pour vibe/wakies/site) :
      (1) les tokens posés sur :root (document entier, hors périmètre mdevs) ;
      (2) color-scheme: light FORCÉ sur :root → peut court-circuiter le
          mode sombre NATIF de l'hôte (scrollbars, champs, autofill) dès
          que la feuille est importée globalement, y compris hors .md-root.

7.2 VOIE « IMPORT GLOBAL MAÎTRISÉ » (simple, non scopée)
    - import '@mdevs/ui/styles.css' une fois dans app/layout.tsx ;
    - neutraliser (1)(2) par une règle HORS COUCHE dans app/globals.css,

8. SIX ARBITRAGES HUMAINS À TRANCHER AVANT LA REFONTA (tableau)
================================================================================

#8.1 ACCENT — LA TENSION MAJEURE
  @mdevs/ui impose --md-accent #4f46e5 (indigo) + --md-focus #4338ca,
  alors que l'AGENTS.md racine : achromatisme strict, QUATRE accents
  sémantiques uniquement, interdiction littérale des teintes Tailwind.
  Options : (a) neutraliser — ThemeProvider accent={une teinte de la
  palette host} ou surcharger --md-accent dans la portée (recommandé pour
  la conformité) ; (b) assumer l'indigo comme cinquième couleur de MARQUE
  et l'enregistrer officiellement dans globals.css + assouplir la règle
  pour ce seul usage. → Décision PRODUIT, pas technique.

#8.2 PILOTE DU THÈME SOMBRE
  Hôte : next-themes, classe .dark sur <html>, PERSISTE. @mdevs :
  data-md-theme sur .md-root, NE PERSISTE PAS, system en CSS.
  Solution : next-themes reste l'unique source de vérité ; le wrapper
  client map resolvedTheme → prop theme du ThemeProvider @mdevs
  (et prop theme="light"|"dark" explicite, pas "system", pour éviter
  le double arbitrage). Vérifier au passage que les --md-* suivent bien :
  le CSS @mdevs ne réagit PAS à .dark nativement — soit on passe par
  la prop, soit par des surcharges .dark { --md-* } hors couche.

#8.3 POLICE
  Hôte : Plus_Jakarta_Sans + JetBrains_Mono (next/font Google, sur <html>,
  --font-sans). @mdevs : Inter 4.1 WOFF2 locale, --md-font, appliquée par
  les composants md- dans .md-root. Conséquence par défaut : deux polices
  coexistent (Jakarta ailleurs, Inter dans les surfaces mdevs).
  Options : (a) assumer le dualisme (les surfaces Liquid Glass « parlent
  Inter ») ; (b) surcharger --md-font: var(--font-sans) dans la portée
  pour tout en Jakarta ; (c) basculer l'hôte sur Inter (remplacer
  next/font par la feuille @mdevs — plus invasif).

#8.4 ICÔNES — LUCIDE vs @mdevs/icons
  lucide-react ^0.577.0 reste dans components/ui (8 fichiers) et dans
  l'app. @mdevs/icons rend les MÊMES NOMS (XIcon, SearchIcon, CheckIcon…)
  avec une AUTRE stratégie couleur (noir/blanc propre ≠ currentColor hérité).
  Risque d'import confus silencieux. Règles à fixer : (a) une seule source
  par arbre de composants (surface mdevs = @mdevs/icons ; composants ui
  legacy = lucide, tant qu'ils vivent) ; (b) imports individuels nommés
  uniquement (@mdevs/icons/controls/x), jamais import * ni barrel catégorie ;
  (c) pas de mélange dans un même écran ; (d) héritage de couleur volontaire

  qui survivront à la refonte gardent leurs XIcon/SearchIcon lucide — la
  migration icône par icône doit être EXPLICITE dans le diff.

#8.5 FRONTIÈRE DES PRIMITIVES
  components/ui (21, shadcn radix-maia, EXCLU DE BIOME) vs @mdevs/ui
